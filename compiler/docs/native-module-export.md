# Exporting Android module APIs

`dcflight.modules.export.export_android(lock, catalog, javap='javap', sdk=35)` verifies an existing `module.lock.json`, inspects locked JAR/AAR bytecode using the selected JDK's `javap -public`, and imports descriptors into `module:<id>:<revision>`. The SDK integer describes the Android compilation context; it is not a claim that every dependency API exists in that Android OS SDK.

AAR `classes.jar` and `libs/*.jar` are inspected alongside transitive JAR artifacts. Each inspected class is passed to javap as an exact temporary class-file path containing the verified archive bytes. Classpath lookup is not used: a JDK boot module therefore cannot substitute its own definition of a class present in the supplied archive. The declared internal class identity must match its archive entry, or export fails. No dependency build scripts, class initializers, annotation processors or application code execute. Temporary archives have tool-controlled names. Archive paths, duplicate paths, class collisions, compressed/expanded sizes and aggregate class counts are bounded; traversal entries fail without extraction. Identical dependency binaries are deduplicated.

The exporter retains public JVM declarations and translates them to the same metalava input used by Android framework APIs. Method overload identities, concrete generics, arrays and wildcard bounds are preserved. Compiler-generated bridge methods are identified by class-file flags and excluded before resolving source signatures. Free generic variables, generic methods, inaccessible owners, unsupported syntax and remaining ambiguous signatures are reported rather than guessed. A wholly unsupported input fails. Kotlin APIs are exposed as their actual JVM-facing Java signatures, not invented Kotlin source wrappers. Javap public listings do not preserve all runtime/type annotations, source nullability, minimum Android API requirements or static nested-class metadata; these remain unknown or conservatively unsupported. They require a richer metadata importer before stronger guarantees.

Two content-addressed snapshots are stored alongside the catalog: exact javap output and converted metalava declarations. Provenance includes lock/artifact SHA256 values, javap version, class count, parser version and unsupported-declaration reasons. `NativeAPI.emit` verifies the converted snapshot hash before producing typed direct Java calls. Copy the catalog's `.sources` directory with its database. Existing module runtime libraries remain native third-party dependencies; the compiler's emitted-call result of `runtimeDependency: null` means no dcflight helper is introduced, not that the selected third-party module vanishes.

`indexed` and `emittable` are descriptor counts. Export sets `compiled: false` and `executed: false`; inspection alone provides neither evidence. `tests/test_module_export.py` compiles a representative fixture JAR, exports it, emits a selected overloaded call and compiles a consumer against that JAR. This is specific fixture verification, not module-wide Android execution evidence. The test needs `JAVA_HOME` pointing at a JDK with javac/javap.

No iOS export support is claimed by this interface. Swift symbolgraph extraction needs a separately configured native SDK/build context and remains a separate integration.

The current parser provenance is `javap-exact-bytecode-to-metalava-v2`, with `classResolution: exact-verified-class-files`. Earlier v1 export reports did not prove that boot-classpath collisions were excluded. Re-export an affected module to replace those descriptors; existing catalogs are not silently re-certified. The regression fixture supplies a java.util.UUID with an archive-only method and verifies that host-JDK randomUUID is absent, then verifies rejection when the same bytes are stored under the wrong class name.

The v3 parser additionally reads ACC_BRIDGE flags from the exact class files via bounded verbose javap inspection. It removes synthetic bridge declarations while keeping the typed source methods. The flag semantics follow the [JVM class-file specification](https://docs.oracle.com/javase/specs/jvms/se24/html/jvms-4.html#jvms-4.6). Existing v2 catalogs can be re-exported to obtain this metadata; prior evidence is not automatically carried forward.
