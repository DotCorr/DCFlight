# Exact Android API version metadata

`dcflight sdk index-android-sdk SDK/android.jar --catalog NEW.sqlite --javap JDK/bin/javap --api-versions SDK/data/api-versions.xml` optionally attaches schema3 version facts to the platform bytecode scope. Without the option, behavior and unknown metadata remain unchanged.

The importer preserves the class-file descriptor adjacent to each exact javap declaration, and binds it through the existing normalization path. It never constructs a JVM descriptor by substituting source type names or guessing generic erasure. Methods match owner binary name, method name and the complete descriptor including return type. Fields match their exact owner/name after ambiguous normalized declarations have been excluded. Nested `$` ownership stays distinct from package `/` paths. Bridge, duplicate and unsupported conversions retain their existing treatment.

The XML and native API snapshots are retained and hashed in catalog provenance alongside the existing SDK JAR hash. Matched records retain class and member since/deprecated/removed facts, extension SDK requirements and module names. Minimum base level is the maximum known class/member since; an omitted member since inherits its class floor. Removed bounds retain the earliest applicable class/member removal. Missing XML identities remain unknown; overriding/inherited methods are not guessed from names. Deprecation is metadata, not automatic rejection.

This identity and since handling follows the [R8 API versions parser](https://r8.googlesource.com/r8/%2B/e2b5855c934224889762e8de0515c43102d9d695/src/test/java/com/android/tools/r8/apimodel/AndroidApiVersionsXmlParser.java), which resolves methods using complete descriptors and combines member introduction with its owner floor. This implementation deliberately does not default an absent class since to an assumed API level.

`APIVersions.check_base_level` checks explicit integer base-version requirements. Its result still has runtimeSupported unknown. Permissions, feature flags, threading and nullability remain unknown; extension requirements are retained but not automatically evaluated. The current public NativeAPI/app operation interface does not accept an Android runtime-target level, so this ingestion alone does not validate every generated application's minSdk or insert runtime guards. Such authoring/build enforcement is a separate typed contract.

Only schema3 with exact positive integer levels is supported. Schema4 and decimal values such as37.2 reject; they are never rounded. Inputs are bounded and DTD/entity declarations rejected. Positive/negative native proof uses one generated SDK_INT_FULL field access: it compiles against SDK36 and fails against SDK35, matching its exact XML since36. No Android code is executed and no shared catalog is modified by that proof.

The final SDK36 import binds all87,959 normalized records to exact JVM descriptors and attaches XML facts to77,934 records;10,025 remain unknown because they have no exact XML entry. An earlier verbose-declaration pass missed511 descriptor bindings: javap verbose expands implicit Object bounds. Collecting descriptors from javap -public -s recovers those identities without rewriting generic bounds, adding452 exact XML matches;59 recovered identities still lack XML entries. The normalized native API source remains byte-identical to the reviewed bytecode-only import, with85,039 emittable members. Metadata counts are distinct from native compilation coverage and physical-device behavior.
