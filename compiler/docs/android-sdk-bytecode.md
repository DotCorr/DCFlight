# Whole platform SDK bytecode inspection

`dcflight sdk index-android-sdk PATH/android.jar --catalog NEW.sqlite --javap JDK/bin/javap` imports all available class namespaces from a platform SDK stub archive. Unlike `index-android-core`, it does not restrict inspection to java/javax/W 3C/SAX. It reuses the same exact-bytecode parser, bridge exclusion and verified nested-class visibility handling. Unsupported Java signatures remain unsupported.

The archive must be named android.jar and have a sibling source.properties describing an integer, non-preview base SDK. An optional `--sdk` must match that metadata. The scope is `sdk-bytecode:LEVEL`; it does not overwrite framework, core-bytecode or another version's scope. Imported origin is `dependencyKind=platform-sdk`, never a native dependency module. The importer stores content-addressed text snapshots, not a runtime jar dependency, engine or bridge. Select the intended version scope when querying overlapping identities.

Bytecode alone loses source metadata. This importer does not recover minimum API introduction, minor API versions, extension requirements, permissions, runtime feature flags, nullability or thread annotations. Missing facts are unknown, not zero or universally available. In particular, javap's verbose output is used for exact bridge/InnerClasses flags, not as a claim that source-retention annotations survived compilation. The resulting emittable marker describes a representable native signature, not application permission or runtime availability.

The installed API 36 archive contains 6,227 classes, all JVM class-file major 52. API 37.2 contains 6,624, also major 52. Java 17 javap and javac spotchecks succeeded against both exact SDK boot-stub jars. This does not mean the compiler can author minor-version SDK dependencies: API 37.2 is explicitly rejected, including when a caller tries `--sdk 37`. Its source.properties says 37.2 and its api-versions.xml uses schema 4 with decimal since values such as 37.1 and 36.1. The current canonical Android SDK snapshot field accepts positive integers only; silently flooring to 37 would misrepresent availability.

`python tools/verify_android_sdk_bytecode.py --android-jar PATH/android.jar --java-home JDK_HOME --output FRESH_DIRECTORY` captures inputs, creates a private catalog and compiles ordinary typed native call probes for every emittable member. It uses Java 8 source/target mode and the selected android.jar as both boot classpath and classpath, avoiding host-JDK core-class substitution. It does not execute probes, alter an emulator, change app SDK settings or publish compiled IDs into a shared catalog. Generated classes are checked for forbidden dcflight/runtime references.

The harness separates classes inspected, members indexed, representable candidates, rejected declarations and native passes/failures. Compiler diagnostics remain visible and a failed batch is never certified. Aggregate native compilation results are target-SDK compatibility evidence only; future source metadata ingestion and device testing have separate denominators.

A future minor-version contract must preserve exact platform identity and api-versions.xml schema semantics through canonical IR, catalog/source metadata, native availability selection and generated build configuration. Adding a decimal parser to this command alone would be insufficient.

Verification runs use one overall deadline across tool identification, indexing and native compilation. Indexing runs in a child process group so its javap descendants share cancellation. The harness checks disk space while children run, bounds captured output before writing beyond the limit, and kills each process group on every exit path. Annotation processing is disabled with `-proc:none`; compiler, SDK, tool and harness fingerprints must remain unchanged. The standalone importer retains its existing per-command bounds; use this verifier when an overall SDK-run deadline is required.
