# Prospective native execution identity

`tools/verify_ios_execution_identity.py --source Fixture.swift --output FRESH_DIRECTORY` performs one new Swift typecheck with a separately linked execution receipt. It does not read or upgrade historical native reports, export descriptors, mutate catalogs, or change the default verifier's compiler fingerprint requirement.

The collector hashes every regular file beneath the selected complete SDK and Xcode toolchain roots, recording directory/link topology and executable modes. This includes SDK interfaces, headers, module maps and precompiled modules, as well as compiler binaries, resource libraries, overlays and plugins in that toolchain. External or dangling symlinks and special files reject. No SDK contents are copied. Resolved swiftc, swift-driver and swift-frontend binary identities are explicitly retained, even when swiftc is a symlink. Snapshots use nonblocking/no-follow regular-file descriptors, per-chunk deadlines and globally bounded directory enumeration. They stream1MiB chunks; bounds are65,536 entries,8GiB total bytes,1GiB per file and180seconds per scan.

The command fixes typechecking, Swift language mode, target triple, SDK and a fresh owned module cache. The runner supplies a small explicit environment with empty owned HOME/TMPDIR, removes inherited compiler search-path variables, and runs from a fresh private directory. OS build and host architecture are retained. Source is limited to1MiB, timeout to600seconds, and diagnostics to8MiB checked while the process runs. Every exit path kills the owned process group, waits for the driver and requires group disappearance before snapshots/publication. Discovery subprocesses have15second timeouts. The owned working tree is checked every250ms against512MiB and a256MiB filesystem free-space floor. A bounded diagnostic file may briefly exceed its threshold between polls.

The full tree snapshot, resolved executable identities, SDK settings, source and producer package hashes are checked after execution. A difference rejects publication, leaving no final receipt. Successful publication uses a fresh-directory rename. Native failure may still produce an execution receipt with a nonzero native report exit code; it never becomes a success claim. Temporary caches are deleted after checks, and retained evidence contains only source, log, native report, manifest and receipt. Command paths reflect their original execution directory; `Verify.swift` remains in the published directory with the recorded bytes.

`execution-receipt.json` binds `native-report.json` by SHA256 and the complete `execution-inputs.json` manifest by SHA256. It records original producer hashes and does not replace any earlier producer. The native report kind is intentionally separate from import-contract reports: this is a bounded baseline for reviewing the collector, not an already integrated whole-SDK producer.

## Explicit trust limits

Before/after snapshots detect persistent changes, not a privileged transient change-and-restore during execution. Host OS libraries are bound by OS build/architecture, not a content-addressed OS image. This local receipt is not signed or externally attested. These limits are recorded in every receipt and must not be silently converted into stronger immutable-image claims by a future compatibility consumer.

No candidate-equivalence reuse is implemented. Before integrating with the ordinary native verifier, review how to attach this execution identity to each import-contract batch without changing its source/import/member contract. A later opt-in consumer must keep both original and consumer identities, regenerate exact candidates and standalone exports, and reject any changed SDK/toolchain/context or missing historical identity. Historical v2 reports without this identity remain historical and cannot be upgraded by collecting today's hashes.
